# msm8998 4.19 移植：分析與 DTB 進度總整（2026-10-25）

接續 [移植清單](msm8998_4.4_to_4.19_sony_port_list_2026-10-25.md) 與 [stage 1 紀錄](msm8998_4.19_stage1_port_notes_2026-10-25.md)。
本文件整併四個子 agent 的結果。**全部為靜態分析或 DTB 編譯，未編核心、未上機。**

## 1. DTB 狀態（已驗證）

- poplar generic、poplar dcm 兩個 DTB 都已編過（主線重編 rc=0，已由主線獨立驗證）。
- k419 工作樹 7 個修改檔，都在 `arch/arm64/boot/dts/vendor/qcom/`，未 commit。
- 修改紀錄：`.tmp/port/dtb_fix_log.md`；建置紀錄：`.tmp/port/dtb_iter_*.log`。
- 主要修改：移除 4.19 不存在的 `&ufs_ice`；NFC clock 改 rpmcc；`pmi8998.dtsi` 補 LED 子節點 label；audio 與 yoshino-common 的舊 `clk_*` 改新巨集；charger xo 改 `RPM_SMD_XO_CLK_SRC`。

**仍是推斷、需實機確認：**
1. audio pinctrl 選了 Sony 的 TLMM gpio69，而非 pm8998 gpio13；`audio-ext-clk.c` 只認 sleep/active。
2. charger xo 來源是依 debugcc 寫法推斷，未對照驅動 binding。
3. 4.19 tri-led 驅動不解析 Sony 的 LED 閃爍屬性，LED 圖樣不生效（不影響編譯與開機）。

## 2. 相機／顯示／音訊（`analysis/camera_display_audio.md`）

**估工：** 相機 9–13、顯示 7–12、音訊 8–12 人日，合計約 24–37 人日（不含實機）。

**最大風險：**
- 相機：`msm_sensor_platform_probe` 與 `msm_sensor_get_dt_data` 在 4.19 不存在（已驗證），4.19 的 `msm_sensor_func_tbl` 為 static，必須同檔補入。
- 顯示：4.19 的 fbdev 完全不解析 `somc,*` 屬性（已驗證，`drivers/video/fbdev/msm` 內無 `somc,` 字串）。這些屬性要搬進 `mdss_dsi_panel_driver.c`。DRM 路徑不適用。4.19 的 `qpnp_lab/qpnp_ibb` 導出函式不存在，面板電源時序會與 stock 路徑衝突。
- 音訊：4.19 techpack 無 AHC、無 sony-hweffect；routing 與 compress 需重做。

**ABI 風險（以 Sony uapi 為準）：**
- `seq_reg_setting` 前端多 `slave_addr`（4.19 無），會靜默錯位。
- SOF 事件與 `msm_sensor_event_data` 僅 Sony 有。
- `csid_params` 4.19 少 3 欄。
- Sony 的 APR 常數（0x10367、0x10F15、0x13333 等）需與 DSP 韌體比對。

**需更正（主線抽查）：**
- 報告說 4.19 q6adm 缺 `adm_get_params(_v2)`。實際上 v1 `adm_get_params` 存在，只缺 `_v2`。
- `camb_position` INVALID（Sony 0x101、4.19 0x102）與 `MAX_CAMERAS`（4 對 6）未能查證，且 `MAX_CAMERAS` 在兩棵樹的定義位置不同。
- DTS 中 somc 屬性數量：報告說 198 處，主線以不同計法得到 829 次出現，兩者都不是唯一計數，需重算。

**未完成：** 未逐 hunk 比對 B2/B3；未檢查 csiphy/csid/ispif/cpp 簽名；未確認目標機 defconfig 的 `CONFIG_SONY_CAM_V4L2` 與 `FB_MSM_MDSS_SPECIFIC_PANEL`；codec（wcd9335、mbhc）未逐行分析。原清單外需補入 `qpnp-labibb-regulator.c` 與 `q6afe.c`。

## 3. USB／UFS／MMC／kgsl（`analysis/usb_ufs_mmc.md`）

**估工：** 約 55–85 小時，另加實機迭代 20–40 小時。

**最大風險：**
1. `dwc3-msm.c`：ID polling、VBUS drop、setsink 在 4.19 完全沒有；依賴的 qpnp-adc、wake_lock 在 4.19 也不存在，VADC 須改用 IIO。
2. `policy_engine.c`：`yoshino.config` 已啟用 `CONFIG_SOMC_CHARGER_EXTENSION`，會改 PD VID/PID、source caps 0.9A 與 PDO 過濾。
3. MMC uim2：GPIO 與 SIM2／SD 托盤連動，屬硬體行為（`uim2-gpios=<&tlmm 39>`）。
4. UFS quirk：4.19 無 revision 欄位，quirk 表在 `ufshcd.c`；Sony 的 Hynix 無條件 `EXTEND_SYNC_LENGTH` 影響範圍大。

**快速可移植：** `host_ext_event.c/h` 與其 Kconfig/Makefile、dwc3 Kconfig、qmp 調校參數、generic.c uevent、sg.c、UFS ioctl 0x53EF（但 `QUERY_ATTR_IDN_FFU_STATUS` 在 4.19 已存在，需略過）、`SCSI_UFS_RESTRICT_TX_LANES`、sdhci uim2 解析。

**kgsl：** Sony 的變更多為 CAF 回補，4.19 大多已含；唯一需決策的是 scratch buffer 特權 revert，需實機 A/B。

**ABI 風險：** `host_ext_event` 的 class 名與 uevent 字串；UFS ioctl 0x53EF 與 struct；PD 身分與 source caps；qusb／ssphy module param；kgsl memtrack 節點名；UIM2 GPIO DT、usb ID polling DT、`qcom,efuse-offset=<5>`。

**未完成：** 4.19 `f_audio_source` 的 alt 結構、ufs Kconfig 是否已有 RESTRICT、4.19 DTS 節點內容未比對。

**產出的 patch：** `analysis/` 內 `dwc3-msm.sony.patch`、`pe.sony.patch`、`qusb.sony.patch`、`qmp.sony.patch`、`mmc.sony.patch`、`usb_misc.sony.patch`，為 Sony 側 diff，未套用。

## 4. 電源／充電（`analysis/power.md`，680 行）

**估工：** 快速可交付（不含 SOMC 充電與 fg 延伸、LED RGB）約 55–100 小時；含 SOMC 充電與 fg 完整搬移約 130–240 小時。

**清單與實際狀況不一致（以 power.md 為準）：**
- `battery.c`：4.19 的 FV votable 已是 `VOTE_MIN`，與 Sony 等效，免改。
- `regulator/core.c` 等：4.19 已含 `regulator_register_ocp_notification` 整套 API，免改；僅 Kconfig 需補 `SOMC_LCD_OCP_ENABLED`。
- `power_supply_sysfs.c`、`bcl_peripheral.c`：清單與任務描述的分類不同，實際需手動合併或重寫。

**關鍵發現：**
1. **DT 已先行、驅動缺口**：yoshino 4.19 DTS 已含約 33 處 `somc,*` 屬性（如 `somc,product-icl-ua`、`somc,jeita-*`、`somc,reg-cfg`），但 4.19 的 power、regulator、thermal、iio、leds、extcon 驅動完全不解析，計數皆為 0。
2. **最大風險是 SOMC 充電與電量計延伸**：`smb-lib.c`（+1659）、`qpnp-smb2.c`（+1050）、`smb-lib.h`（+189）、`qpnp-fg-gen3.c`（+1244）。分岔點在 `CONFIG_SOMC_CHARGER_EXTENSION`（smb-lib.c 107 處、qpnp-smb2.c 38 處）。我已驗證：Sony 的 `smb-lib.c` 有 192 個不重複 `smblib_*` 識別字，4.19 有 177 個，缺 25 個。
3. **4.19 缺的依賴**：`linux/wakelock.h`、`qpnp_get_pin_config`（4.19 無 qpnp-pin，PMIC GPIO 改用 `pinctrl-spmi-gpio.c`）。
4. **LCD OCP 是跨模組依賴**：labibb 的導出 API（`qpnp_lab_set_*`、`qpnp_ibb_set_*`）被 `mdss_dsi_panel_driver.c` 與 `mdss_fb.c` 呼叫，需與顯示同步。
5. **4.19 已有等效**：regulator OCP 通知框架、`qpnp-regulator.c` 的 VS OCP 通知、`battery.c` 的 FV VOTE_MIN。

**建議優先序（前 5 名）：** ldo_vibrator 與 qns_system（直接搬）→ power_supply 屬性表（只 append）→ extcon VBUS-DROP → rradc `somc,reg-cfg` → msm-poweroff OEM_F。SOMC 充電與 fg 延伸建議不整份搬，拆成功能 patch，或先不啟用。

**未確定：**
- Sony 上層（充電 daemon、QNS daemon、閃光燈 sysfs 使用者）是否依賴 somc sysfs。
- yoshino 採用的 fuel gauge 是 fg-gen3、gen4 還是 qg。
- ADC decidegC、BCL VBAT TLOW 2.4V、WLED 目標節點的實際數值。
- `SOMC_CHARGER_EXTENSION` 是否為必要。

## 7. 相機 userspace 對應哪一套 uapi（2026-10-25 查證）

- 專案內的 `camera/cacao/libcammw_util`、`libsomc_chokoballpal` 不 include `msm_cam_sensor.h`，不是感測器 ABI 的使用者。
- 實際使用感測器 ABI 的是原廠 HAL 二進位：`~/lineageos/vendor/sony/yoshino-common/proprietary/vendor/lib/`。
  - `libmmcamera2_sensor_modules.so` 含 `VIDIOC_MSM_SENSOR_CFG`、`translate_sensor_seq_reg_setting`，以及 SOF 事件字串（`MCT_EVENT_CONTROL_SOF`、`SOF = %d ...`）。
  - `libcammw.so` 含 `sony_camera_get_sensor_driver`、`sony_camera_platform_i2c_read/write`，表示它呼叫的是 Sony 的感測器平台介面。
  - `libmmcamera2_cpp_module.so` 使用 `/dev/v4l-subdev%d`。
- 4.19 uapi 沒有 SOF 事件與 `msm_sensor_event_data`，`seq_reg_setting` 也缺 `slave_addr`（見第 2 節的 ABI 清單）。
- 結論：原廠 HAL 依賴 Sony 的 uapi 與 Sony 的感測器平台介面，相機應走 **Sony 平台路徑**。
- 未完成：blob 內 struct 的實際佈局與 ioctl 編號未做反組譯比對，目前是字串層級的證據。

## 8. 反組譯比對 VIDIOC_MSM_SENSOR_CFG 的結果（未完成）

- 兩棵樹的 ioctl 定義相同：`_IOWR('V', BASE_VIDIOC_PRIVATE + 1, struct sensorb_cfg_data)`，BASE_VIDIOC_PRIVATE = 192。ioctl 編碼的 size 欄位取決於 `sizeof(struct sensorb_cfg_data)`，所以兩邊的值會因結構大小不同而不同。
- 在 `libmmcamera2_sensor_modules.so` 中搜尋 `_IOWR('V',193,*)` 的編碼（以 literal 形式、movz/movk 立即值兩種）都找不到，無法從 blob 反推出 size 欄位。
- 嘗試以 clang 的 `-fdump-record-layouts` 直接取得兩邊的結構大小，因為 kernel header 的依賴（asm/*、barrier.h、timeval 等）無法在主機環境編譯，也未完成。
- 結論：目前仍只有字串層級的證據（見第 7 節）。要得到結構大小，需要：
  1. 在目標 kernel 的編譯環境中（有完整 `asm/` 與 `linux/` header）產生 layout，或
  2. 對 blob 中實際呼叫 `ioctl` 的位置做完整的函式追蹤（可能透過間接呼叫或 wrapper，不是單一 literal）。

## 9. 完整 kernel 環境產生的 layout（2026-10-26）

量測方法：`.tmp/port/abi/probe_size*.c` 對 uapi 結構取 `sizeof`，以 `clang -S -emit-llvm` 輸出常數（不依賴執行檔）。
- 4.19：使用 `.tmp/out419` 內 `msm_sensor.o` 的實際 kernel 編譯旗標（`.msm_sensor.o.cmd`），即完整 kernel 環境。
- Sony 4.4.302：`.tmp/out_sony` 以 `msm8998` defconfig 執行 `make prepare` 產生 generated headers，再以 uapi 標頭加上 `include/generated` 編譯；旗標為手動組出（未加 `-include kconfig.h`，probe 只包含 uapi 標頭，故影響不大）。

| 結構 | 4.19.325 | Sony 4.4.302 |
|---|---|---|
| `struct sensorb_cfg_data`（VIDIOC_MSM_SENSOR_CFG 的參數） | 184 | 184 |
| `struct csid_cfg_data` | 16 | 16 |
| `struct msm_camera_i2c_seq_reg_setting` | **24** | **32** |
| `struct msm_camera_i2c_seq_reg_array` | 1028 | 1028 |
| `struct msm_camera_i2c_reg_setting` | 24 | 24 |
| `struct msm_camera_i2c_reg_array` | 8 | 8 |

結論：
- `VIDIOC_MSM_SENSOR_CFG` 的 ioctl 編碼在兩棵樹相同（0xC0B856C1，size=184），所以 ioctl 號碼本身不能區分兩者。
- 不相容發生在內部：`sensorb_cfg_data` 的 union 內有指向 `seq_reg_setting` 的指標，Sony 的結構多出 8 bytes，與第 2 節報告所指的 `slave_addr` 欄位方向一致，但尚未直接從標頭確認是哪個欄位。4.19 讀取時若位移不同，會造成錯位，且不一定立即報錯。
- 這是量測到的差異，已取代第 8 節的「尚未完成」。blob 內部實際使用的偏移仍未反組譯比對，但已足以支持「相機走 Sony 平台路徑」的建議。

附註：Sony 樹的 `make prepare` 在 vDSO 步驟失敗（clang 組譯 `vgettimeofday`），但 generated headers 已產生，對本測量無影響；該步驟的暫存 `.s` 檔是 kernel 建置程序寫入系統 `/tmp`，不是本專案的暫存，但仍記錄於此。

## 25. 追查 keymaster 失敗的根因鏈（2026-10-27）

- 開機早期 log：`Failed to enable shmbridge, rsp = 0, ret = -95` 與 `shmbridge is not supported by this target`。對應 `TZ_SHM_BRIDGE_ENABLE`（SIP owner 2、svc 0x0C、cmd 0x1C，SMC id 0x42000C1C）被 TZ 拒絕。
- 之後 `qtee_shmbridge_enabled = false`，4.19 的 qseecom 仍透過 shmbridge 相關路徑做 listener 註冊。
- 失敗的 SMC `0x72000206` 解碼為 owner 50（QSEE OS）、svc 2（LISTENER）、cmd 6 = `TZ_OS_REGISTER_LISTENER_SMCINVOKE_ID`，在 qseecom 的 shared-buffer 註冊路徑（直接呼叫，無 fallback）共失敗 8 次。
- Sony 4.4 的 qseecom 沒有 shmbridge（0 處參照，也沒有 qtee_shmbridge 驅動），同一個 TZ 在 4.4 上可用。
- 結論：根因鏈是「TZ 不支援 shmbridge → 4.19 的 qseecom 註冊路徑與 Sony 4.4 不同 → listener 註冊被 TZ 拒絕 → keymaster 不可用 → cryptfs init_user0 失敗 → recovery 重開」。
- 尚未完全證實：TZ 拒絕 0x72000206 的確切參數條件（sb_phys 來源、大小、權限）。下一步需要在 qseecom 的 listener 註冊處加入參數記錄，或讓 4.19 在 shmbridge 不支援時改走 4.4 的原始實體位址路徑。

## 30. cryptfs init_user0 失敗的真正根因（2026-10-27 03:40）

結論：**/data 使用舊式 ICE（`fileencryption=ice`，UFS 內建 ICE v2 硬體加密），4.19 沒有對應的 ICE v2 路徑，所以讀到的 `/data/misc/vold/...` 內容是亂碼。** 先前「keymaster/qseecom 有問題」的方向是錯的。

證據鏈：
1. 4.4 開機（adb root）：`lsattr -d /data/misc/vold` 顯示 `E`（加密）旗標，`user_keys/de/0/version` 內容為正常的 `1`。4.19 讀同一個檔，vold 印出 `Version mismatch, expected 1 got <亂碼>`，`cryptfs init_user0` 失敗，init 重啟到 recovery。
2. 22.2 vendor 的 `fstab.qcom`：`/data ... fileencryption=ice`（沒有 `inlinecrypt`）。
3. 4.19 的 fscrypt 只有在 ext4 以 `-o inlinecrypt` 掛載時才走硬體；否則 `ice` 模式退回軟體 `xts-aes-ce`（log：`fscrypt: ice using implementation "xts-aes-ce"`）。已在 `fs/crypto/inline_crypt.c` 讓 `FSCRYPT_MODE_PRIVATE` 忽略該掛載選項，並開啟 `FS_ENCRYPTION_INLINE_CRYPT`、`ENABLE_LEGACY_PFK`、`CRYPTO_DEV_QCOM_ICE`。之後 `Version mismatch` 與軟體 XTS 訊息消失，但出現下一層阻礙。
4. 下一層：`crypto_qti_program_key:SCM call Error: 0xffffffa1`（-95）→ `blk-crypto: Failed to acquire keyslot ... Falling back to crypto API`。4.19 的 `drivers/soc/qcom/crypto-qti-tz.c` 用新的 SCM（`TZ_ES_CONFIG_SET_ICE_KEY_CE_TYPE` = svc ES cmd 0x5）寫金鑰，Sony A9 的 TZ 不支援。4.4 的 `security/pfe/pfk_ice.c` 用舊 SCM：`TZ_ES_SET_ICE_KEY`（cmd 0x2，參數 index≥2、key phys/len=32、salt phys/len=32）與 `TZ_ES_INVALIDATE_ICE_KEY`（cmd 0x3）。
5. 另外 msm8998 的 UFS HCI 是 v2，4.4 的 `ufs-qcom-ice.c` 是逐請求寫 ICE 暫存器（`ICE_CTRL_INFO_1/2_n`，以 `req->tag` 為索引，含 LBA、key index、bypass 位元；`hw_ver.major == 3` 才免設定）。4.19 的 `ufshcd-crypto-qti` 走 JEDEC／v3 的 UTRD 路徑，對 v2 硬體不適用。

要讓舊 A9 vendor 的 `/data` 可讀，需要在 4.19 補上：舊 SCM 寫金鑰（含 key+salt 切分、key index 對應）＋ ICE v2 的逐請求暫存器設定（或 UFS 請求描述符對應）。這是一個獨立的移植項目。

## 33. ICE 解密成功，4.19 首次開到系統（2026-10-27 04:30）

結論：**msm8998 的 UFS 是 HW v3（`REG_UFS_HW_VERSION` = 0x30010000），ICE 版本 3.0.65**，不是 ICE v2，§30 第 5 點「逐請求暫存器」的假設是錯的（4.4 的 `hw_ver.major == 3` 分支本來就免設定，改走請求描述符 dword_0 = cc_index | 0x800000、dword_1/3 = DUN）。4.19 的 UTRD 路徑格式與 4.4 相同，真正缺的只有兩件事：

1. 金鑰寫入：Sony A9 TZ 不支援新 SCM（svc ES cmd 0x5/0x6），要用 4.4 `pfk_ice.c` 的舊指令：`TZ_ES_SET_ICE_KEY`（cmd 0x2，參數 index、key phys/32、salt phys/32）與 `TZ_ES_INVALIDATE_ICE_KEY`（cmd 0x3）。64 位元組衍生金鑰前 32 = key、後 32 = salt；fscrypt 已做過一次 be32 交換，寫入前要再換一次還原。
2. 金鑰索引：TZ 保留 0、1 給 FDE，索引須在 2..31；keyslot 數量夾到 30，寫入與 UTRD 的 cc_index 都用 `slot + 2`。

- `include/linux/crypto-qti-common.h`：旗標宣告。
- `drivers/scsi/ufs/ufshcd-crypto-qti.c`：讀 DT `qcom,legacy-ice-v2`、keyslot 數夾到 30、legacy 時略過 HCI 能力檢查、UTRD key slot +2。

### 41.13 UBWC 與 ION 快取錯誤（2026-10-28）

- logcat：`qdgralloc CleanBuffer: ION_IOC_CLEAN_INV_CACHES failed with error - Invalid argument` 與 `UnlockGrallocBuffer: GRALLOC1_FUNCTION_UNLOCK failed` 重複出現（launcher 程序）。
- 4.19 ION 實作（`drivers/staging/android/ion/ion-ioctl.c`）：`buffer_fd = fd >= 0 ? fd : handle`，再 `dma_buf_get`；`offset > size` 或 `length > size - offset` 時回 `EINVAL`。4.4 則是 `client->dev->custom_ioctl` 路徑。
- 合成格式：`mdp/dump` 顯示三個圖層都是 `RGBA_8888_UBWC`（format=45）。
- 屬性：`hwcomposer.qcom.so` 含有 `vendor.gralloc.disable_ubwc`。
- A/B 方法：設定 `vendor.gralloc.disable_ubwc=1`，重啟 `vendor.gralloc-2-0` 與 `vendor.hwcomposer-2-3`，再重啟 framework。第一次只重啟 framework 時屬性未生效（gralloc 程序未重啟），錯誤仍在。
- 結果（服務重啟後）：合成恢復（`Play Count` 增加，`Total pipes=1`），格式為 `RGBX_8888`（非 UBWC），`CleanBuffer` 錯誤數為 0。
- 結論（待螢幕確認）：UBWC 路徑的 ION 快取維護失敗；UBWC 關閉後錯誤消失。顏色是否正常需要實際觀察螢幕。
- 注意：`vendor.gralloc.disable_ubwc` 只能在執行時設定（`/vendor` overlay 重開機後不保留），不是修正本身。
